## T-8E01 — Создать личность автоматизации

**Только вручную — у GitHub нет API для этого действия.**

GitHub не даёт ни одного способа создать GitHub App через `gh` или REST API — только
форма в браузере. Личность нужна, чтобы действия конвейера были подписаны не вашим
личным аккаунтом, а отдельной, узко-урезанной identity: видно в логе не «teratron
сделал X», а «сделал именно automation-бот с вот этим точным набором прав».

### Перед началом

- Вы вошли на GitHub под аккаунтом-владельцем репозитория `teratron/booking`.
- Под рукой — таблица разрешений ниже: заполняется один раз, ошибиться дорого
  (создавать App заново — не страшно, но лишний раз проверить не помешает).

### Шаги

**1.** Откройте форму создания GitHub App

`Settings → Developer settings → GitHub Apps → New GitHub App` (в личных настройках
аккаунта, если репозиторий у вас на личном аккаунте — как сейчас; если позже переедете
в организацию, форма та же, но в настройках организации).

Имя — любое узнаваемое, например `booking-release-bot`. Homepage URL — просто адрес
репозитория.

**2.** Отключите webhook

Снимите галочку **Active** в блоке Webhook. Эта identity не слушает события — только
вызывает API от своего имени. Активный webhook без обработчика — лишняя поверхность
отказа и ничего не даёт.

**3.** Выставьте Repository permissions ровно по таблице ниже

Это самый важный шаг — именно этот набор реализует «withheld» из спецификации.

| Permission | Значение | Зачем |
| --- | --- | --- |
| `Contents` | Read and write | Читать код, мёржить PR, пушить теги. |
| `Pull requests` | Read and write | Открывать/обновлять/мёржить PR в `develop` и `master`. |
| `Metadata` | Read-only | Обязательный минимум, GitHub включает его сам. |
| `Issues` | Read and write | Комментировать и подписывать выполненные действия. |
| `Checks` | Read-only | Видеть статус гейта, не запускать проверки самостоятельно. |
| `Administration` | **не трогать — Access: None** | «Withheld» буквально: identity не может менять свои же права. |
| `Secrets`, `Environments`, `Actions` | **не трогать — Access: None** | Никакого доступа к секретам и настройкам окружений. |

> **Моя рекомендация.** Не выдавайте больше, чем в таблице, даже «на всякий случай» —
> весь смысл этой identity в том, что она физически не может одобрить собственный PR и
> не может тронуть branch protection. Если чего-то не хватит позже — права App можно
> расширить одной правкой в этой же форме, откат назад (после того как чем-то уже
> пользовались) устроен куда неприятнее.

**4.** Where can this GitHub App be installed?

Выберите **Only on this account** — не «Any account». Публично устанавливаемое
приложение здесь не нужно и не задумано.

**5.** Создайте App, затем сгенерируйте приватный ключ

После **Create GitHub App** откройте страницу приложения и внизу нажмите **Generate a
private key** — скачается файл `*.pem`. Это единственный момент, когда ключ виден
целиком; повторно скачать тот же файл нельзя, только перевыпустить новый.

Запишите с той же страницы: **App ID** (число вверху страницы).

**6.** Установите App в репозиторий `teratron/booking`

Кнопка **Install App** в левом меню страницы приложения → выберите репозиторий →
**Install**. После этого появится **Installation ID** (виден в адресной строке после
перехода на страницу установки, число после `/installations/`).

**7.** Не добавляйте её как reviewer

Ни в список required reviewers у `production`-окружения (он уже настроен на вас), ни в
`.github/CODEOWNERS`. Оставить эту identity вне списков — не бездействие, а часть
контракта: identity, способная и запросить, и одобрить собственное продвижение, не
является гейтом вообще.

### Как проверить

```bash
# authenticate as the app, then:
gh api /app --jq '.permissions'
# ожидается: contents=write, pull_requests=write,
# и НИЧЕГО про administration

gh api repos/teratron/booking/environments/production \
  --jq '.protection_rules[].reviewers[].reviewer.login'
# App не должен появиться в этом списке
```

**Готово, когда** App ID, Installation ID и файл приватного ключа у вас сохранены (не в
репозитории!) — они понадобятся на шаге 2, как раз для яруса repository secrets.

## T-8E03 — Загрузить секреты по трём ярусам

**Только вручную — значения существуют только у вас.**

Сейчас не настроено ни одного секрета — ни на уровне репозитория, ни в окружении
`production` (проверено напрямую перед тем, как писать эту инструкцию). Три яруса — не
формальность: каждый виден ровно тому job'у, которому положен, и ни одному другому. Это
и есть механизм, который делает верным правило «секреты никогда не путешествуют вместе
с кодом».

| Ярус | Держит | Доступен |
| --- | --- | --- |
| **1 · Repository secrets** | Ключ карт (`MAP_TILE_KEY`) и приватный ключ App'а из шага 1 | только job'у `build` |
| **2 · Environment secrets (production)** | Секрет обхода maintenance-режима (`MAINTENANCE_BYPASS_SECRET`) | только job'у `deploy`, и только после одобрения reviewer'а |
| **3 · `.env` на самом хосте** | Все runtime-credentials приложения: база, Redis, S3/R2, почта, Sentry, капча, бэкапы | только запущенным контейнерам, никогда — runner'у |

### Перед началом

- Шаг 1 закрыт — App ID, Installation ID и `.pem`-файл под рукой.
- У вас есть реальный production-хост (или хотя бы понятно, откуда возьмутся его
  реквизиты — БД, Redis, S3/R2, SMTP, Sentry).
- `gh` установлен и авторизован (`gh auth status`) — быстрее, чем через веб-интерфейс,
  но подойдёт и он.

### Шаги

**1.** Ярус 1 — секреты репозитория

```bash
gh secret set MAP_TILE_KEY --repo teratron/booking
# вставьте ключ провайдера тайлов (MapTiler/Stadia — см. l2-tech-stack.md §5.11)

gh secret set AUTOMATION_APP_ID --repo teratron/booking
# App ID из шага 1

gh secret set AUTOMATION_APP_PRIVATE_KEY --repo teratron/booking < path/to/app.pem
# содержимое .pem-файла целиком
```

> **Моя рекомендация.** Регистрационные данные для `ghcr.io` отдельным секретом заводить
> не нужно — `build` уже аутентифицируется штатным `GITHUB_TOKEN`, и второй credential
> тут был бы просто дублирующей поверхностью для утечки.

**2.** Ярус 2 — секрет окружения `production`

```bash
gh secret set MAINTENANCE_BYPASS_SECRET \
  --repo teratron/booking --env production
# любая случайная строка длиной от 32 символов, например:
openssl rand -hex 32
```

Это значение передаётся в `php artisan down --secret=` — тот, кто его знает, может
просматривать сайт во время maintenance-окна раньше остальных посетителей. Держите его
отдельно от паролей людей.

**3.** Ярус 3 — `.env` на самом хосте

Скопируйте `.env.production.example` из корня репозитория в `.env` прямо на
production-хосте и заполните пустые значения: пароль БД, пароль Redis, ключи S3/R2,
SMTP, Sentry DSN, ключи капчи, e-mail для уведомлений о бэкапах.

> **Моя рекомендация.** Заполняйте этот файл *только* редактором прямо на хосте
> (SSH + `nano`/`vim`) либо через секрет-менеджер хостинг-провайдера. Никогда не
> готовьте заполненную копию локально и не передавайте её через чат, почту или, тем
> более, коммит «временно, потом уберу» — история git не забывает.

### Как проверить

```bash
gh secret list --repo teratron/booking
# ожидается: MAP_TILE_KEY, AUTOMATION_APP_ID, AUTOMATION_APP_PRIVATE_KEY

gh secret list --repo teratron/booking --env production
# ожидается: MAINTENANCE_BYPASS_SECRET

git log -p --all -S'BEGIN PRIVATE KEY'
# должно быть пусто — ни один секрет никогда не попадал в git
```

**Готово, когда** все три команды выше показывают ожидаемое — а `.env` на хосте не
существует нигде, кроме самого хоста.

## T-8T03 — Провести репетицию деплоя и отката

**Только вручную — агент не может быть доказательством за человека.**

Смысл этого шага — не «конвейер технически работает» (это уже доказано тестами), а
«человек, который инструкцию не писал, довёл релиз и откат до конца, читая только
`docs/operations/en/deploy.md` и `rollback.md`, без подсказок». Агент не может сыграть
эту роль даже теоретически — прочитать собственноручно написанную инструкцию и
«убедиться», что она понятна, ничего не доказывает.

### Перед началом

- Одноразовый хост — VM, которую не жалко потерять (DigitalOcean/Hetzner droplet на
  час-два, или локальная VM). **Не** реальный production.
- На хосте установлен Docker + Docker Compose и склонирован репозиторий.
- На хосте установлен self-hosted GitHub Actions runner с метками `self-hosted` и
  `production` — без них job'ы `deploy`/`verify`/`rollback` просто не запустятся.
- На хосте лежит заполненный `.env` (шаг 2, ярус 3) — тестовые значения БД/Redis/S3
  достаточно, реальные production-креды сюда не нужны.
- Исполнитель — не вы (или не тот, кто в этой сессии правил конвейер). Коллега,
  знакомый разработчик, или вы сами, но спустя достаточно времени, чтобы честно забыть
  детали.

### Шаги

**1.** Поднимите одноразовый хост

Минимальные требования — как у `docker-compose.production.yml`: Docker 24+, 2 vCPU /
4 GB RAM достаточно для рехёрсла (не для реального трафика).

**2.** Установите self-hosted runner с нужными метками

Settings репозитория → **Actions → Runners → New self-hosted runner**. На шаге
настройки укажите дополнительные метки: `./config.sh ... --labels production` —
базовая метка `self-hosted` добавляется автоматически.

**3.** Передайте исполнителю только два файла

`docs/operations/en/deploy.md` и `rollback.md` — больше ничего. Не объясняйте на
словах, что «на самом деле» нужно нажать; если инструкция чего-то не покрывает, это и
есть находка репетиции.

**4.** Исполнитель проводит настоящий релиз по `deploy.md`

От выбора номера версии и тега до визита на живой (тестовый) сайт — все девять шагов из
документа, без сокращений.

**5.** Исполнитель проводит настоящий откат по `rollback.md`

Не «представим, что откатываем» — реальный запуск процедуры отката на этом же
одноразовом хосте, до состояния «предыдущая версия снова работает».

**6.** Запишите репетицию так же, как записана репетиция восстановления

По образцу `docs/restore-rehearsal.md` — что именно произошло, какие шаги пришлось
*импровизировать* (это самое ценное в записи), и какая правка в документе эту
импровизацию убирает.

> **Моя рекомендация.** Не переписывайте `deploy.md`/`rollback.md` «по памяти» после
> репетиции — правьте *прямо во время* неё, в момент, когда исполнитель споткнулся.
> Формулировка, которая ясна автору документа, и формулировка, которая ясна человеку,
> впервые видящему процедуру, — систематически разные вещи, и разрыв между ними виден
> только в моменте.

### Критерий приёмки

```plaintext
1. Релиз и откат оба завершились успешно
2. Оба оставили запись на странице Releases с digest'ом образа
3. Исполнитель — не автор процедуры
4. Каждый импровизированный шаг отражён правкой в документе
   до закрытия фазы
```

**Готово, когда** запись репетиции лежит рядом с `docs/restore-rehearsal.md`, а оба
файла в `docs/operations/en/` не нуждаются в устных дополнениях.

## После трёх шагов

Фаза 8 закрывается — все 23 задачи выполнены. Дальше первый реальный релиз запускается
тем же способом, что описан в `deploy.md`: тег → зелёный `scan-migrations` → сборка →
ваше подтверждение как reviewer'а → деплой → автоматическая проверка здоровья → запись
в Releases. Обычные, не затрагивающие чувствительные зоны изменения после этого смогут
доходить до `master` без отдельного одобрения — правило, которое вы уже включили на
обеих защищённых ветках.

Отметить любую из трёх задач выполненной в `phase-8.md` и запустить `/magic.run main`
дальше можно в любой момент — достаточно сказать об этом.
