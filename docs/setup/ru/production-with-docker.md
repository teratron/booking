# Развёртывание на настоящем сервере, с Docker

Это **спроектированный** способ запуска живого сайта. Это **разовая
настройка**, обычно выполняемая разработчиком. После того как она сделана
один раз, каждая новая версия сайта выходит **сама** через процесс релиза из
[`../../operations/ru/deploy.md`](../../operations/ru/deploy.md) — эту страницу вы
не повторяете.

Если сервер уже настроен и вам нужно только выпустить новую версию, вы не на
той странице: используйте
[`../../operations/ru/deploy.md`](../../operations/ru/deploy.md).

Сначала прочитайте [`overview.md`](overview.md), если ещё не читали.

## Что даёт эта настройка

- Живой сайт на вашем домене, по HTTPS.
- Каждый релиз собирается один раз автоматическим конвейером, утверждается
  названным человеком, разворачивается с коротким окном обслуживания и
  автоматически проверяется на работоспособность — с **откатом одной
  командой**, если проверка не прошла.
- Ночные бэкапы базы данных и еженедельные бэкапы медиа в хранилище,
  отдельное от самого сайта.

## Кто должен это делать

Разработчик или человек, уверенно работающий с Linux-сервером, DNS домена и
настройками проекта на GitHub. Потребуется создавать учётные записи и секреты
у внешних провайдеров. На первый раз закладывайте полдня.

## Перед началом

Подготовьте:

- **Linux-сервер** под вашим контролем (виртуальная машина у любого
  хостинг-провайдера подойдёт). Разумный стартовый размер: 2 CPU, 4 ГБ RAM,
  40 ГБ диска; см. [`../../php-fpm-capacity.md`](../../php-fpm-capacity.md) для
  подбора пула веб-воркеров под реальный трафик.
- **Доменное имя** с DNS, направленным на этот сервер.
- **Docker Engine** и **плагин Compose**, установленные на сервере.
- **Аккаунт S3-совместимого хранилища** — Cloudflare R2 или Backblaze B2 — с
  **двумя bucket**: одним для медиа, одним для бэкапов. Они должны быть
  раздельными. См.
  [`../../production-provisioning.md`](../../production-provisioning.md).
- **Аккаунт почтового релея** (Postmark, Amazon SES, Resend или
  self-hosted-релей) с учётными данными SMTP. См.
  [`../../mail-and-error-tracking.md`](../../mail-and-error-tracking.md).
- **Ключ картографических тайлов** от MapTiler (или другого провайдера).
  Публичные тайл-серверы OpenStreetMap для продакшена использовать нельзя.
- Необязательно, но рекомендуется: проект **Sentry** или self-hosted
  **GlitchTip** ради адреса приёма отчётов о сбоях (DSN).
- **Доступ к этому проекту на GitHub** с правом менять настройки репозитория
  и окружения.

## Шаги

### 1. Подготовьте сервер

Установите Docker и плагин Compose, затем подтвердите:

```
docker --version
docker compose version
```

Разместите копию проекта на сервере (автоматика деплоя сама выгружает код, но
серверу нужны `docker-compose.production.yml`, папка `docker/` и ваш `.env`):

```
git clone <адрес репозитория> /opt/booking
cd /opt/booking
```

### 2. Заведите внешние сервисы

Создайте и запишите учётные данные для:

1. **Bucket медиа** и **bucket бэкапов** (раздельные).
2. **Почтовый релей** — SMTP-хост, порт, имя пользователя, пароль.
3. **Ключ картографических тайлов**.
4. Необязательно — **DSN Sentry / GlitchTip**.

Подробности и заметки по провайдерам:
[`../../production-provisioning.md`](../../production-provisioning.md),
[`../../mail-and-error-tracking.md`](../../mail-and-error-tracking.md).

### 3. Создайте продакшен-файл настроек

```
cp .env.production.example .env
```

Затем отредактируйте `.env` и заполните **каждый пробел**. Важные:

| Настройка | Значение |
| --- | --- |
| `APP_ENV` | `production` |
| `APP_DEBUG` | `false` |
| `APP_URL` | `https://ваш-домен` (точно, с `https://`) |
| `APP_KEY` | Сгенерируйте: `docker compose -p booking-production -f docker-compose.production.yml run --rm app php artisan key:generate --show`, затем вставьте сюда значение `base64:...`. |
| `ADMIN_PANEL_PATH` | Неочевидный путь на ваш выбор (не `admin`). Запишите его — так ваш персонал попадает в панель. |
| `CABINET_PANEL_PATH` | Путь кабинета владельца (по умолчанию `cabinet` подходит). |
| `DB_PASSWORD` | Надёжный пароль, который вы выбираете сейчас. |
| `REDIS_PASSWORD` | Надёжный пароль, который вы выбираете сейчас. |
| `SESSION_SECURE_COOKIE` | `true` (сайт только по HTTPS). |
| `AWS_*` | Endpoint, регион, ключ, секрет и имя bucket медиа. |
| `MEDIA_CDN_URL` | Адрес вашего CDN перед bucket медиа, если он есть. |
| `MAIL_*` | Хост, порт, имя пользователя, пароль релея; `MAIL_FROM_ADDRESS` на вашем домене. |
| `SENTRY_LARAVEL_DSN` | DSN из шага 2, если вы его создали. Не оставляйте пустым после запуска. |
| `MAP_TILE_KEY` | Ваш ключ картографических тайлов. |
| `BACKUP_AWS_BUCKET` | Имя bucket **бэкапов** (не медиа). |

Держите этот файл доступным для чтения только владельцу (`chmod 600 .env`).
Он никогда не попадает в Git и не покидает сервер.

### 4. Настройте HTTPS перед сайтом

Собственный веб-вход продакшен-настройки слушает обычный порт 80 внутри
сервера. Поставьте перед ним одно из:

- **Cloudflare** (или другой CDN) перед доменом, с шифрованием до origin; или
- **Обратный прокси на самом сервере** (nginx, Caddy или Traefik),
  держащий TLS-сертификат и проксирующий на порт 80.

См. [`../../production-provisioning.md`](../../production-provisioning.md) для
схемы CDN, которую ожидает проект.

### 5. Подключите автоматический конвейер релиза

Именно это делает будущие релизы делом одного клика. На GitHub, в настройках
этого проекта:

1. **Реестр контейнеров** — конвейер публикует собранный образ в собственный
   реестр контейнеров GitHub, используя встроенный токен; дополнительных
   учётных данных не нужно.
2. **Окружение `production`** с **обязательным ревьюером** — тем одним
   человеком, который должен утвердить каждый релиз до того, как он коснётся
   сервера.
3. **Self-hosted runner**, установленный **на этом сервере**, с метками
   `self-hosted` и `production`. После этого сервер сам *забирает* работу с
   GitHub; входящий доступ к серверу не нужен.
4. **Секреты**, которые читает конвейер:
   - `MAP_TILE_KEY` — тот же ключ, что и в `.env` (конвейер вшивает публичную
     половину в собранные скрипты).
   - `MAINTENANCE_BYPASS_SECRET` — случайная строка на ваш выбор; она
     позволяет оператору релиза предпросматривать новую версию во время окна
     обслуживания.

Полное описание конвейера и его задач:
[`../../release/pipeline.md`](../../release/pipeline.md).

### 6. Выполните первый релиз

Следуйте [`../../operations/ru/deploy.md`](../../operations/ru/deploy.md) с шага 1.
Первый релиз особенный лишь в одном: поскольку ещё ничего не запущено,
автоматика деплоя пропускает окно обслуживания и просто всё стартует. Всё
остальное — отправка тега версии, проверка безопасности, сборка, утверждение
ревьюером, проверка работоспособности, запись релиза — идентично любому
последующему релизу.

Когда всё закончится, собственный адрес работоспособности сайта отвечает:

```
curl -i https://ваш-домен/up      # ожидается: HTTP/.. 200
```

### 7. Загрузите стартовые данные

Автоматика деплоя приводит **структуру** базы в актуальное состояние, но
**не** загружает стартовые справочные данные (языки, страны, уровни
территорий, типы объектов, роли, права). Без них сайт не работает. Выполните
один раз на сервере:

```
docker compose -p booking-production -f docker-compose.production.yml \
  exec app php artisan db:seed --force
```

Это также создаёт администратора `test@example.com`. **Немедленно** либо
удалите его, либо смените e-mail и пароль — см. шаг 8.

**Должно получиться:** `Database seeding completed successfully`.

### 8. Создайте настоящего администратора

**Не** оставляйте на живом сервере учётную запись `test@example.com`.
Откройте терминал внутри приложения и создайте нормальную учётную запись
(замените имя, e-mail и пароль):

```
docker compose -p booking-production -f docker-compose.production.yml exec app php artisan tinker
```

Затем вставьте:

```php
$user = App\Models\User::create([
    'name' => 'Site Administrator',
    'email' => 'you@ваш-домен',
    'password' => Illuminate\Support\Facades\Hash::make('длинный-надёжный-пароль'),
    'email_verified_at' => now(),
]);
app(App\Services\Authorization\RoleGrantService::class)
    ->grantRole($user, 'chief_administrator', $user);
App\Models\User::where('email', 'test@example.com')->delete();
```

Введите `exit`, чтобы выйти. Роль `chief_administrator` требует второго
фактора входа, поэтому ваш первый вход проведёт вас через настройку приложения
-аутентификатора. См.
[`first-run-and-daily-tasks.md`](first-run-and-daily-tasks.md).

### 9. Подтвердите и передайте

- `https://ваш-домен/en` открывается по HTTPS, оформлен, с вашим контентом.
- `https://ваш-домен/<ваш путь админки>` показывает страницу входа, и вы
  можете войти администратором из шага 8.
- `https://ваш-домен/horizon` показывает дашборд очереди (при входе
  администратором).
- На GitHub существует запись «Release» для выпущенной версии, помеченная как
  успешная.

## Если что-то не работает

- **Конвейер релиза показывает красный шаг** → не трогайте сервер вручную.
  Следуйте
  [`../../operations/ru/read-a-failed-pipeline.md`](../../operations/ru/read-a-failed-pipeline.md).
- **`/up` возвращает не 200 после первого релиза** → автоматика релиза
  откатывается сама; если восстановить работоспособность не удаётся, она
  останавливается и оставляет сайт в режиме обслуживания для человека. См.
  [`../../operations/ru/restore.md`](../../operations/ru/restore.md).
- **Панели без стилей на живом сайте** → в собранном образе нет ассетов
  панелей; это проблема сборки, а не то, что чинят на сервере. Сообщите
  разработчику.
- **Что-то ещё** → [`troubleshooting.md`](troubleshooting.md), затем
  разработчику.
