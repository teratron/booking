# Устранение проблем при установке

Конкретные проблемы, встречавшиеся при запуске этого проекта, и что решает
каждую из них. Найдите свой симптом.

## Порт уже занят

**Симптом:** `docker compose up` падает с «port is already allocated» или
«bind: address already in use», называя номер вроде `8300`, `5433`, `6379`,
`9000`, `9101`, `1025`, `8325`.

**Причина:** этот номер уже слушает другая программа на вашей машине. В
Windows целые диапазоны могут быть также **зарезервированы Hyper-V** — bind в
зарезервированном диапазоне падает с ошибкой *прав доступа*, а не «занято».
Проверить зарезервированные диапазоны:
`netsh interface ipv4 show excludedportrange protocol=tcp`.

**Решение:** переназначьте конфликтующий порт, не редактируя отслеживаемый
compose-файл. Создайте `docker-compose.override.yml` рядом с
`docker-compose.yml` — Docker объединяет их автоматически. Пример, увод
PostgreSQL с `5433`:

```yaml
services:
  postgres:
    ports: !override
      - "15432:5432"
```

Затем в `.env` задайте `DB_PORT` равным **новому** номеру (здесь `15432`),
чтобы инструменты на хосте подключались куда надо. Контейнеры приложения не
затронуты — они всегда обращаются к PostgreSQL как `postgres:5432` в
собственной сети Docker. Тот же приём работает для любого сервиса; `redis`,
`minio`, `nginx` (`8300:80`) и `mailpit` публикуют свой хостовый порт так
же.

## Неверный адрес / битые ссылки / перенаправления, которые не открываются

**Симптом:** сайт перебрасывает вас на домен, который браузер не может
открыть; или страница грузится, но без стилей; или все ссылки и картинки
указывают на неверный хост.

**Причина:** `APP_URL` в `.env` не совпадает с адресом, по которому вы
реально открываете сайт. Приложение строит из `APP_URL` каждую ссылку,
перенаправление, URL ассета и canonical-тег.

**Решение:**

1. Задайте `APP_URL` равным **точному** адресу, который вы вводите в
   браузере — схема, хост и порт. Примеры: `http://localhost:8300` (локально
   Docker), `http://127.0.0.1:8000` (встроенный сервер), `https://ваш-домен`
   (продакшен).
2. Очистите кеши — некоторые фрагменты навигации кешируются с вшитым старым
   адресом:

   ```
   php artisan config:clear
   php artisan cache:clear
   ```

   (С Docker добавьте перед ними `docker compose exec app`.) На продакшене с
   Docker это делает автоматика деплоя; на ручном сервере после этого
   выполните `php artisan config:cache`.

## `php -v` показывает не ту версию (не 8.5)

**Симптом:** `composer install` или `php artisan` жалуется на версию PHP,
либо `php -v` показывает 8.1 / 8.3 / 8.4.

**Причина:** обычный `php` в вашем `PATH` — более старая установка. Часто в
Windows с Laravel Herd, где смена версии по умолчанию не всегда переписывает
глобальный ярлык.

**Решение (любое из):**

- Вызывайте версионированный бинарник явно в каждой команде — напр. `php85`
  вместо `php`, или полный путь вроде
  `C:\Users\<вы>\.config\herd\bin\php85\php.exe`.
- В вашем менеджере версий PHP сделайте 8.5 глобальной версией по умолчанию
  (в Herd: иконка в трее → PHP → 8.5), затем откройте **новый** терминал.
- Настройте IDE / task runner проекта прямо на бинарник 8.5.

Инструкция с Docker полностью обходит это — в контейнере всегда 8.5.

## Панели (персонала / кабинета) отображаются как текст без стилей

**Симптом:** `BASE/portal-admin` и `BASE/cabinet` открываются, но выглядят
как голый HTML-документ без цветов, отступов и работающих кнопок.

**Причина:** стили и скрипты панелей не опубликованы. Они намеренно не
хранятся в Git, поэтому свежая установка должна их сгенерировать.

**Решение:**

```
php artisan filament:assets
```

(С Docker добавьте перед этим `docker compose exec app`.) Повторяйте и после
каждого обновления набора инструментов панелей.

## HTTP 500 без записи в логе (Docker)

**Симптом:** страницы возвращают пустой `500`, а в
`storage/logs/laravel.log` нет соответствующей записи.

**Причина:** папка `storage/` или `bootstrap/cache/` недоступна для записи
веб-пользователю, так что даже логгер не может открыть свой файл. Случается,
когда bind-mount несёт владельца с хоста.

**Решение:**

```
docker compose exec app chown -R www-data:www-data storage bootstrap/cache
```

Стартовый скрипт контейнера делает это автоматически, но изменение прав,
сделанное после этого на хосте, может снова всё сломать.

## Всё медленно под Docker (Windows / macOS)

**Симптом:** каждая страница открывается несколько секунд; кликать по
админ-панели мучительно.

**Причина:** Docker в Windows и macOS раздаёт папку проекта в контейнер через
медленный слой общего доступа к файлам. PHP читает тысячи файлов на запрос;
накладные расходы складываются.

**Решение / обходной путь:** для тяжёлой интерактивной работы запускайте
**PHP на хосте**, оставляя базу, Redis и хранилище в Docker:

1. Держите `docker compose up -d` запущенным (ради `postgres`, `redis`,
   `minio`, `mailpit`).
2. В `.env` направьте `DB_HOST`/`REDIS_HOST`/`AWS_ENDPOINT`/`MAIL_HOST` на
   `127.0.0.1` и **опубликованные** порты (`DB_PORT=5433` и т. д.).
3. Задайте `APP_URL` равным адресу, на котором будете обслуживать, напр.
   `http://127.0.0.1:8000`.
4. Запустите `php artisan serve --port=8000` на хосте (PHP 8.5).

После этого страницы отвечают в разы быстрее. Верните хосты в `.env` на имена
Docker-сервисов, когда вернётесь к полностью-Docker-настройке.

## `pnpm install` встаёт, а потом падает внутри контейнера

**Симптом:** `docker compose exec app pnpm install` печатает вопрос об
удалении пакетов и затем прерывается, потому что не может прочитать ваш
ответ.

**Решение:** запускайте неинтерактивно:

```
docker compose exec -e CI=true app pnpm install
```

## `migrate` или `migrate:fresh` падает

- **Упоминает `postgis`, `pg_trgm` или `unaccent`:** нужные расширения
  PostgreSQL не установлены в целевой базе. Под Docker они создаются
  автоматически при первом старте; без Docker выполните операторы
  `CREATE EXTENSION` из [`local-without-docker.md`](local-without-docker.md)
  шаг 1 для нужной базы.
- **Упоминает ошибку кеша или подключения:** Redis недоступен. Некоторые
  миграции обращаются к кешу по ходу, поэтому Redis должен быть поднят для
  полного `migrate:fresh`, а не только для очереди.
- **«database ... does not exist»:** создайте её, либо (Docker) удалите том
  базы и дайте ей переинициализироваться: `docker compose down -v`, затем
  `docker compose up -d` (это стирает локальные данные).

## Загруженные картинки дают 404, или «bucket does not exist»

**Симптом:** сайт работает, но картинки не загружаются и не отдаются.

**Причина (Docker):** bucket'ы хранилища не созданы. Одноразовый контейнер
(`minio-init`) создаёт их при `docker compose up`; если он не отработал или
вы запустили только часть сервисов:

```
docker compose up -d minio-init
```

**Причина (без Docker):** создайте bucket'ы `booking-media` и
`booking-backups` в консоли MinIO или клиентом `mc`, в соответствии с
`AWS_BUCKET` и `BACKUP_AWS_BUCKET` в `.env`.

## Данные PostgreSQL пропали после смены образов

**Симптом:** после смены Docker-образа база выглядит пустой или сообщает, что
не инициализирована.

**Причина:** образы PostgreSQL 18 хранят данные на один уровень каталога
иначе, чем более старые образы. Compose-файл проекта это уже учитывает;
обычный виновник — вручную отредактированный путь тома.

**Решение:** держите строку тома `postgres-data:/var/lib/postgresql` из
отслеживаемого `docker-compose.yml` ровно как есть. Если данные уже
потеряны, повторно выполните `migrate --seed`.

## Фоновые задачи никогда не выполняются (без Docker)

**Симптом:** письма-уведомления не приходят; задачи по расписанию, бэкапы и
перегенерация карты сайта не выполняются.

**Причина:** три фоновых процесса не запущены. Docker запускает их за вас;
ручная настройка тоже должна.

**Решение:** запустите (и поддерживайте живыми через Supervisor в
продакшене):

```
php artisan horizon
php artisan schedule:work
php artisan pulse:work
```

## Заблокирован в панели двухфакторной аутентификацией

**Симптом:** вы настроили второй фактор, потеряли устройство и коды
восстановления, войти не можете.

**Решение:** очистите настройки второго фактора этой учётной записи из
терминала, затем войдите только паролем и настройте заново:

```
php artisan tinker
```

```php
App\Models\User::where('email', 'you@ваш-домен')->update([
    'two_factor_secret' => null,
    'two_factor_recovery_codes' => null,
    'two_factor_confirmed_at' => null,
]);
```

## Всё ещё не получается

- У упавшего **конвейера релиза** на продакшене есть своё руководство:
  [`../../operations/ru/read-a-failed-pipeline.md`](../../operations/ru/read-a-failed-pipeline.md).
- Во всех остальных случаях соберите точную команду, которую вы выполнили, и
  её полный вывод, и передайте и то и другое разработчику. Скриншота красной
  ошибки без её текста недостаточно, чтобы действовать.
