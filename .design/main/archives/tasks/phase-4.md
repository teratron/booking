# Stage 4 Tasks — Discovery & Catalog

**Phase:** 4
**Status:** Done
**Strategic Goal:** A guest can search from Home or browse the Catalog and
reach a filtered, sorted, paginated, map-synchronized result set built from
one shared query contract — the acquisition surface the whole marketplace
depends on, per `l1-platform-foundation.md`'s discoverability invariant.

## Track Structure

Honest execution shape: `(A01 ‖ A02) → (B01 ‖ C01 ‖ C02) → C03 → T`.

- **Track A** (query contract + shared widgets) has no dependency on Phase 3
  and can start immediately — it only reads Phase 1's `hotel`/`room`/`review`/
  `amenity` tables, all of which have carried data since Phase 1's schema.
- **B01** (Home) needs both A01 (the query) and A02 (the date/guest pickers).
- **C01** (catalog list) needs only A01. **C02** (filter sidebar) needs only
  the URL-param contract A01 defines, not A01's runtime output directly — it
  is genuinely dispatchable in parallel with C01, not sequenced behind it.
- **C03** (map) needs the filtered/paginated result set C01+C02 together
  produce, so it is sequenced after both, not parallel with either.

## Decisions Carried Into Decomposition

<!-- Elective forks resolved here per magic.md §7 (DA-8/DA-9) — narrated, not asked. -->

- [DR] Home's result list is the same catalog query as the Catalog route
  (default params: `sort=popularity`, no filters, `page=1`), not an
  independent editorial feed. Criterion: `l1-hotel-discovery.md` §6
  Implementation Notes states the filter/sort/paginate contract should be
  "designed once and shared by Home and Catalog, not duplicated" — a fully
  independent editorial feed would need its own curation tooling that
  doesn't exist and isn't scoped anywhere in this project's specs; the
  simpler reading that matches the explicit shared-contract instruction is a
  single query, called with different default params per route. (Override:
  `/magic.spec` to record Home as a genuinely separate curated feed if that
  reading is wrong.)
- [DR] Curated category shortcuts ("sea vacation", "mountains", "eco
  tourism") are pre-defined filter-parameter presets in the UI layer (a
  hardcoded `{label, params}` list), not a new `hotel.category` schema
  column. Criterion: no categorization field exists anywhere in the Phase 1
  schema or any spec's data model; the spec describes them only as
  "one-click entry points into a pre-filtered catalog view" — behaviorally
  identical to a saved filter combination, not new domain data. Avoids a
  schema migration for a UI convenience feature. (Override: `/magic.spec` +
  a schema migration if these are meant to be owner-assignable/admin-curated
  rather than fixed presets.)
- [DR] Map integration uses **Leaflet + OpenStreetMap tiles** (`react-leaflet`,
  no API key) rather than Google Maps or Mapbox. Criterion: this project has
  no billing/API-key infrastructure set up for a paid maps provider (unlike
  Vercel Blob, which needed exactly one env var); Leaflet+OSM works
  immediately in dev with zero external account setup, and `hotel.latitude`/
  `hotel.longitude` (plain `doublePrecision` columns, Phase 1) are provider-
  agnostic — swapping providers later doesn't touch the data model.
  (Override: `/magic.spec` to add a Map Provider entry to `l2-tech-stack.md`
  if Google Maps/Mapbox's richer styling or geocoding is actually needed.)
- [DR] The map (T-4C03) plots the full filtered result set's coordinates,
  not just the current page. Criterion: `l1-hotel-discovery.md` §3 says pins
  update on "a filter change," not on a page change, and a map showing only
  8-20 of e.g. 60 filtered hotels while claiming to be "synchronized with
  the filtered result set" would misrepresent what's actually available at
  that filter combination. At this project's expected data scale (no bulk
  seed/import tooling exists yet), fetching all matching coordinates
  alongside the paginated card query is not a performance concern.
- [DR] No sidebar facet for check-in/check-out dates, even though the hero
  search collects them. Criterion: `l1-hotel-discovery.md` §5.2's Filter
  Facets list (Location, Accommodation type, Star rating, Price range,
  Amenities, Room facilities, Family, Wellness) does not include dates —
  date-range availability filtering is a room-level reservation concern
  (`l1-room-reservation.md`, Phase 6), not a hotel-level catalog facet. The
  hero search's dates carry through as a query param for later Phase 6 use,
  they just don't gate which hotels are shown at the catalog layer.

### [T-4C02] Catalog filter sidebar

- **Spec:** l1-hotel-discovery.md §5.2 Filter Facets
- **Status:** Done
- **Assignment:** Agent
- **Verify:** component test — toggling each facet control updates the URL's corresponding query param and resets `page` to 1 (a filter change must not leave the user stranded on a now-out-of-range page); clearing all filters returns to the unfiltered URL.
- **Handoff:** C01 renders the result set these filters narrow; C03's map reflects the same narrowed set.
- **Changes:**
  **Design choice**: the whole sidebar is one native `<form method="GET" action="/catalog">`, not client-side controls wired to `router.push`. Every input's `name` becomes a query param the instant a browser submits the form — single-select facets are radio groups (`accommodationType`, `minStarRating`), multi-select facets are checkbox groups (`amenityIds`, `roomAmenityIds`), free-text/numeric facets are plain `text`/`number` inputs (`destination`, `minPrice`, `maxPrice`) — with zero client JS, zero manual href-building, and the "reset page to 1 on any filter change" requirement falls out for free (the form has no `page` input, so submitting never carries a stale one forward). The current `sort` rides along as a hidden input so applying a filter doesn't silently revert an explicit sort choice. `Clear filters` is a plain `<Link href="/catalog">`. This is a genuinely different interaction model from T-4C01's sort/pagination controls (individual `<Link>`s, one click = one navigation) because the facet set has both single-click-appropriate controls (radios/checkboxes) and free-text ones (price/location) that can't be meaningfully "toggled" per keystroke — bundling everything behind one explicit "Apply" action, as real catalog UIs do, avoids a jarring half-Link/half-form sidebar.
  **Real data-model gap found, resolved with a documented curation call (not a schema change)**: `l1-hotel-discovery.md` §5.2 lists "Amenities (hotel-level)", "Family / children", and "Wellness / treatment" as three separate filter facets — but `amenityGroupEnum` (`hotel | room | bathroom | bedroom | general`, Phase 1) has no data axis for a family/wellness split, and the seeded amenity table (`seed-amenities.ts`) has zero amenities that are unambiguously family- or wellness-specific among its 8 "hotel"-group rows. Inventing an undocumented name-keyword heuristic (e.g. "Spa" → wellness) to fake three sections would be fragile, silently wrong the moment the seed list changes, and not remotely what `catalogQuerySchema`'s own `amenityIds` param supports (a single flat facet).
