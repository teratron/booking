## Task Detail

### Track A — Addressing Foundation

**[T-6A01] Per-language slug resolution and the territory-hierarchy URL grammar**
Replace the placeholder public addressing with the specified grammar: territory paths
mirror the hierarchy (`/{lang}/{country}/{region}/{district}/{settlement}` and a typed
catalog beneath it), while object profiles sit on a deliberately **flat**
`/{lang}/o/{object-slug}` so that recategorizing or reassigning an object never breaks
a ranked URL. Resolve through a single indexed lookup on language, entity type, and
slug. The denormalized `territory_translations.full_slug_path` column already exists
and is written by the territory administrator on reparenting — this task makes it the
read path, backfills the rows no administrator has touched, and adds the uniqueness
constraint the lookup assumes.
**One host, language as the leading path segment — settled, not open.** There are no
language subdomains and no per-country domains. Alternates are therefore path swaps on
the same host, canonicals always name that host, and no part of this task should be
built to keep a subdomain migration cheap.
*Verify:* `docker compose exec app php artisan test --filter=SeoUrlGrammarTest` — asserts
a five-level territory path resolves to the right record, that an object URL is
unchanged by reparenting its territory, and that two territories in different countries
may share a leaf slug. Plus `composer quality` green with all 21 existing call sites of
the former route names updated.

**[T-6A02] Redirect table — model, administration, same-operation creation on slug change**
Give the existing `redirects` table its model, its administrator-editable resource, and
the resolution middleware that consults it on a slug miss before rendering 404. Wire
redirect creation into the same operation as the slug change, for slug edits, territory
reparenting, and archived content — a redirect added in a later step is added after the
traffic is already lost.
*Verify:* `docker compose exec app php artisan test --filter=RedirectResolutionTest` —
asserts a changed slug serves 301 from the old path, that the redirect row is created
within the same transaction as the slug write, and that a slug is never reused while a
redirect claims it.

### Track B — Metadata, Indexation, Structured Data & Sitemaps

**[T-6B01] Per-language SEO metadata fields and the resolution ladder**
Today only `seo_title` and `seo_description` exist on the translation tables. Add the
rest of the per-language set the specification requires — canonical URL, indexation
directive, Open Graph title, description and image, and the search-engine text block —
across every entity that needs it, then build the three-step resolution ladder:
explicit value, else an administrator-defined template rendered from entity data, else
derived from the entity name and its territory. Empty metadata is never shipped.
*Verify:* `docker compose exec app php artisan test --filter=MetadataResolutionTest` —
one case per ladder rung, asserting the template rung fires only when the explicit value
is absent and that no rendered page emits an empty title or description.

**[T-6B02] Indexation policy — the matrix, filter allowlist, pagination canonicals, robots**
Make indexability a data-driven per-page attribute the rendering layer reads, never a
hard-coded per-route decision. Filtered catalog views are **not indexable by default**;
a filter combination becomes indexable only through an explicit administrator entry in
an allowlist. Paginated views beyond page 1 are indexable and canonical to themselves,
not to page 1. Non-public objects, the owner cabinet, and the back office are excluded
and disallowed in an administrator-manageable robots directive.
*Verify:* `docker compose exec app php artisan test --filter=IndexationPolicyTest` — a
case per row of the specification's indexation matrix, including that a single-filter
catalog URL emits `noindex` until allowlisted and page 2 canonicalizes to itself.

**[T-6B03] Structured data and breadcrumbs, gated on module state**
Emit type-appropriate structured data — lodging, food establishment, place, article,
offer — plus a breadcrumb list on every page below home. Gate offer-availability
emission on booking-module state for that object: emitting availability the portal
cannot honour is a durable trust penalty, not a cosmetic error.
*Verify:* `docker compose exec app php artisan test --filter=StructuredDataTest` —
asserts each page type emits its own entity, that breadcrumbs are present below home,
and specifically that an object page emits **no** offer availability while the booking
module is disabled.

**[T-6B04] Sitemap index — paginated per-language artefacts, regenerated by job**
A sitemap index referencing per-language, per-entity-type sitemaps, each paginated
within the format's limits, written as static artefacts by a scheduled job rather than
computed per request. Only indexable pages appear. Requires adding
`spatie/laravel-sitemap`, which the project's package list names but which is not yet
installed.
*Verify:* `docker compose exec app php artisan test --filter=SitemapGenerationTest`
against the realistic-volume seeder — asserts the index references one child per
language and entity type, that pagination triggers past the format limit, and that a
`noindex` page never appears in any child.

**[T-6B05] SEO administration screen and health warnings**
The back-office surface where an SEO specialist manages titles, descriptions, addresses,
canonicals, robots directives, Open Graph data, territory page copy, filter indexation,
title templates, the sitemap, redirects, error pages, and structured data — plus the
health warnings that make a catalog this size maintainable: missing title, missing
description, duplicate address, missing translation, over-length title, and page
excluded from indexing. At portal scale nobody finds a duplicate slug by browsing.
*Verify:* `docker compose exec app php artisan test --filter=SeoAdministrationTest` —
asserts each of the six warning types fires against a deliberately broken fixture, and
that the screen is permission-gated for a user without the SEO grant.

### Track C — Portal-Wide Reporting

**[T-6C01] Derived figures across every aggregation dimension**
`AnalyticsReport` already serves period-scoped counts filterable by object, banner,
territory, country, type and language. What is missing is the derived set the
specification names: most viewed objects, most popular categories, banner
click-through rate, new owner count, new object count, bump count, published promotion
count, and pending moderation count. Compute them against the aggregate tier only,
never against raw events, and keep them exportable through the existing filter set.
*Verify:* `docker compose exec app php artisan test --filter=PortalReportingTest` — one
assertion per derived figure against a fixed fixture with known counts, plus a query-count
assertion proving no figure reads `stat_events`.

**[T-6C02] Traffic-source and page-popularity reporting in the back office**
`TrafficSourceRecorder` already records a coarse channel, referring host, and campaign
tag on a visit's first event. Nothing surfaces it. Aggregate it by channel in the back
office alongside page popularity — never as a per-visitor list, which is what the
coarse shape exists to prevent.
*Verify:* `docker compose exec app php artisan test --filter=TrafficSourceReportTest` —
asserts the six channels aggregate correctly, that the internal channel is reported
distinctly from referral, and that no endpoint or export can return a per-visitor row.

### Track D — Public API

**[T-6D01] API module gate, versioned routing, and the disabled-capability 404**
Register the API as a gateable module, disabled at portal scope by default — the module
registry currently carries only reviews, guest accounts, booking, and payment. Add the
versioned route file and its bootstrap registration. A request against a disabled module
returns **404, not 403**: a 403 confirms the capability exists.
*Verify:* `docker compose exec app php artisan test --filter=ApiModuleGateTest` —
asserts 404 with the module disabled and a non-404 with it enabled, across both an
existing and a non-existing endpoint so the two are indistinguishable when disabled.

**[T-6D02] API client and token model — issuance, scoping, revocation, journalling**
The `api_clients` table and Sanctum's `personal_access_tokens` both already exist from
the schema pass; neither has a model. Build the client and token models, the
administrator resource that registers a client and issues a scoped, expiring token, and
the revocation path that takes effect immediately rather than at next expiry. A token's
scope — resources, countries, categories — resolves through the same scoping model as
administrative permissions, not a second authorization system. Store hashes only;
display the clear value once. Journal every issuance, revocation, and scope change.
*Verify:* `docker compose exec app php artisan test --filter=ApiTokenLifecycleTest` —
asserts a revoked token is rejected on its very next request, that the clear value is
absent from storage, and that all three lifecycle events appear in the action journal.

**[T-6D03] Read endpoints as a layer over the existing catalog retrieval contract**
The read-only collection and detail endpoints, built as a layer over
`CatalogQueryService` rather than a parallel query path — two implementations of
"list objects in a territory, tier-ordered" will diverge, and the divergence is a
revenue bug. Collections return the same ordering the catalog renders. Apply the
published-only visibility filter in the shared query layer, not per endpoint. Responses
are language-negotiated and fall back exactly as pages do.
*Verify:* `docker compose exec app php artisan test --filter=ApiReadContractTest` —
asserts every collection endpoint's ordering matches the catalog's for the same filter
set, and that a pending, rejected, archived, or hidden record is absent from every
endpoint.

**[T-6D04] Rate limiting, consumption measurement, and generated documentation**
Per-token rate limiting with per-token configurable limits, applied **before** the query
runs — a limiter that runs post-query offers no protection to the database it protects.
Record consumption per token and per endpoint through the existing event pipeline.
Publish documentation generated from the same schema definitions that validate requests,
at a stable versioned address, so contract and documentation cannot drift.
*Verify:* `docker compose exec app php artisan test --filter=ApiRateLimitTest` — asserts
429 with a retry hint at the configured limit, a query-count assertion proving the
limiter short-circuits before any catalog query, and that the generated document lists
every registered route.

### Track T — Validation

**[T-6T01] Indexation invariant — nothing non-public is ever indexable**
A single test that sweeps every registered public route and asserts the negative case
holistically rather than per-task: no pending, rejected, archived, or hidden object, no
cabinet or back-office path, and no multi-filter catalog URL is ever indexable or
present in any sitemap.
*Verify:* `docker compose exec app php artisan test --filter=IndexationInvariantTest` —
route-registry driven, so a route added later without an indexation decision fails the
test rather than shipping silently.

**[T-6T02] API parity invariant — never a visibility or ordering the site would not give**
Assert the API and the website agree, by comparing them directly: for a matched filter
set, the API's result identity and order equal the catalog page's, and any record absent
from the page is absent from the API. This is the test that would catch a "neutral
ordering" regression, which is a revenue defect rather than a display bug.
*Verify:* `docker compose exec app php artisan test --filter=ApiParityInvariantTest`
against seeded volume, comparing API payload order against the rendered catalog's own
retrieval for at least three filter permutations including an unfiltered first page.

**[T-6T03] Redirect permanence and slug stability**
Assert the durable promises: a changed slug always leaves a permanent redirect, a slug
is never silently reused, a redirect chain resolves rather than looping, and territory
reparenting leaves every affected descendant path redirected.
*Verify:* `docker compose exec app php artisan test --filter=SlugStabilityInvariantTest`
— includes a reparent of a mid-tree territory with descendants, asserting a redirect
exists for every descendant path, and a deliberate two-hop chain asserting no loop.

## Track Ordering

**Phase 6 is three-wide: `(A → B) ∥ C ∥ D → T`.** Unlike Phase 5, which funnelled
through a single retrieval gate, this phase has three largely disjoint concerns — and
saying so precisely matters, because two of them can start immediately while the third
cannot.

`T-6A01` is the phase's hard gate and its highest-cascade task, but it differs in kind
from `T-5A03` or `T-2A02`: those were greenfield contracts adopted by later work, while
this one is a **retrofit** of addressing that 21 existing files already depend on.
Every task in Track B consumes the URL grammar — canonical URLs, sitemap entries, and
breadcrumbs are all statements about addresses — so Track B cannot begin until it lands.
`T-6A02` also depends on it, since a redirect's target is expressed in the new grammar.

Within Track B the ordering is `B01 → B02 → (B03 ∥ B04) → B05`. `T-6B01` adds the
indexation directive that `T-6B02` governs; `T-6B04` may only include pages `T-6B02` has
declared indexable; `T-6B05` administers the fields all four establish, so it lands last.

**Track C is fully independent** of A, B, and D. It reads `stat_dailies`, which Phase 3
built and Phase 4 already reports against — no task here touches a route, a URL, or a
token. It can run first, last, or concurrently.

**Track D is independent of A and B.** The API is a layer over `CatalogQueryService`
(Phase 5) and does not consume the SEO URL grammar — its resources are addressed by
identifier, not by slug path. Internally it is a strict chain: `D01 → D02 → D03 → D04`.
The module gate must exist before tokens are checked behind it, tokens before endpoints
are scoped, and endpoints before a limiter or a generated document can describe them.

One cross-track contract is scheduled rather than discovered mid-run: **`T-6B02` and
`T-6D03` must share one published-only visibility filter, not build two.** Both specs
ask for the same thing in their own language — the indexation policy excludes non-public
records, and the API applies its visibility filter in the shared query layer. Two
implementations would drift, and the drift would expose unmoderated content on whichever
side was forgotten. Whichever task lands first owns the filter; the second consumes it.

Track T runs last. All three of its invariants are cross-track by construction —
`T-6T01` sweeps the route registry Track B populates, `T-6T02` compares Track D against
Phase 5's own rendering, and `T-6T03` exercises Track A's redirect promises against
territory operations built back in Phase 2.

## Planning Audit

**Optimism bias.** `T-6A01` is the one to distrust. Read as "add some routes" it looks
small; it is a rewrite of the addressing every public page built in Phase 5 depends on,
and each of that phase's feature tests asserts against generated URLs. Two things
genuinely reduce it: `territory_translations.full_slug_path` already exists, and the
public route group was deliberately built as a swappable scaffold with the eventual
grammar noted at the call site. What remains real is the reverse resolution, the
backfill for territories no administrator has ever edited (only one code path writes
that column today), and the uniqueness constraint the lookup will assume.

`T-6B04` is the second underestimation risk. At the seeded volume this project
benchmarks against, sitemap generation across several entity types in every active
language is a paginated batch job, not a call to a helper — and the package it needs is
named in the project's own package list but is not installed.

`T-6D03` reads like eleven endpoints of routine serialization. The actual risk is that
`CatalogQueryService` was built for a Blade and Livewire caller; exposing it through a
JSON contract without either duplicating the query or leaking internal shapes is the
task's real content.

**Hidden dependencies.** Claiming four-way parallelism here would be false in the same
way it was for Phase 1. The honest shape is three-wide, and Track D's internal chain is
strictly sequential, so the effective parallel degree is three at the start and drops to
two once Track C finishes — it is the shortest track by a wide margin. The shared
visibility filter between `T-6B02` and `T-6D03` is the one genuine cross-track resource
bottleneck, which is why it is written into §Track Ordering rather than left to be
discovered when the two implementations disagree.

**Cascade risk.** `T-6A01` blocks all five Track B tasks and one Track A task — six of
sixteen — and a broken landing fails every Phase 5 feature test simultaneously, which
would make the failure look like a regression in work that is already complete. Running
it against the existing public test suite rather than only its own new test is the
mitigation. `T-6D01` carries the second-largest blast radius relative to its size: the
404-versus-403 decision is security-adjacent, cheap to get wrong, and invisible until
someone probes for it, which is precisely why `T-6T02` exists as a separate invariant.

**Plan stability.** All three specifications remain `RFC`, as every phase before this
one was planned and executed under. Two open questions touched this phase at planning
time; **one is now closed.** The deferred question of country-specific domains — the
one genuinely consequential for a task rather than merely for a document, since
`T-6A01` is what would have made the answer permanent — was settled by the project
owner on 2026-08-15: **a single host, with language as the leading path segment, and no
subdomains of any kind.** That removes the phase's only irreversible fork. It also
means `T-6A01` should not carry defensive structure to keep a subdomain migration
mechanical; the specification's §2 note and `l1-localization.md` §7 both anticipate a
migration that is no longer planned, and building for it would be paying for optionality
the owner has declined.

The remaining question — the absence of any stated rate-limit figure or data-licensing
position — is a business decision `T-6D04` should pick a defensible default for rather
than wait on, since the design is deliberately conservative enough that opening it later
is a policy change rather than a redesign.

## Standing Constraints

- Filtered catalog views are **not indexable by default**. A filter combination becomes
  indexable only by explicit administrator decision — this is the portal's principal
  defence against near-duplicate proliferation across three dimensions that multiply.
- Structured data must not overstate. Where the booking module is inactive, an object
  page must not emit offer availability it cannot honour.
- Collection endpoints return the **same ordering the catalog renders**. A neutral
  ordering would let a consumer build a competing listing that bypasses the portal's
  revenue model entirely.
- The API exposes published, public data only — at every tier, for every token.
- A disabled API module returns 404, not 403: a 403 confirms the capability exists.
- Slug changes create a permanent redirect; slugs are never silently reused.
- **Object URLs stay flat** (`/{lang}/o/{slug}`) while territory URLs mirror the
  hierarchy. An administrator may move an object between cities and resorts, and under a
  hierarchical object URL every such move would break a ranked page.
- **One host; language is the leading path segment; no subdomains.** Not a default
  awaiting review — a settled decision. Alternates are path swaps on the same host, and
  neither language subdomains nor per-country domains are to be built toward.
- **One published-only visibility filter, shared** between the indexation policy and the
  API's query layer. One forgotten filter exposes unmoderated content.
- Rate-limit before doing work. A limiter that runs after the query protects nothing.
- The API read contract layers over `CatalogQueryService`; it never opens a second
  retrieval path.
- Sitemaps are generated artefacts written by a job, never computed per request.
